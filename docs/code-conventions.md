# 通用代码规范

## 基本原则

- 正确性和可读性优先于技巧性；选择团队容易理解和维护的实现。
- 模块保持高内聚、低耦合，依赖方向清晰，不形成循环依赖。
- 只实现当前明确需求，避免预先构建没有使用场景的扩展点。
- 同一规则、配置或数据只保留一个权威来源。

## 命名与结构

- 名称表达用途和领域含义，避免无意义缩写、临时编号和误导性命名。
- 函数、类和模块保持单一职责；当一段代码需要多次使用“并且”描述职责时，应考虑拆分。
- 公共抽象只包含真正稳定且共享的部分；相似但会独立变化的代码不强行合并。
- 常量替代散落的魔法值；有限取值采用当前语言中清晰、可校验的表达方式。

## 边界与错误

- 在输入、外部接口和持久化边界执行校验，内部代码依赖已验证的不变量。
- 错误不得静默忽略；错误信息应便于定位，同时避免泄露敏感数据。
- 网络、文件和外部服务调用应按风险考虑超时、取消、重试和幂等性。
- 日志记录必要上下文，但不记录密码、令牌、完整个人信息或其他敏感内容。

## 注释与文档

- 注释解释“为什么”和约束，不重复代码已经清楚表达的“做什么”。
- 公共接口、非直观算法和重要取舍应有简洁说明。
- 行为、契约或目录发生变化时，同步更新相关文档。

## 测试与质量

- 测试验证可观察行为、核心规则、边界条件和关键失败路径。
- 修复缺陷时，条件允许应先补充能复现问题的测试。
- 测试应可重复、相互隔离，不依赖隐式执行顺序或真实生产资源。
- 使用仓库已配置的格式化、静态检查和测试命令；未选型前不因规范初始化而安装工具。

## 依赖与安全

- 新增依赖前评估必要性、维护状态、许可证、体积和安全影响。
- 包管理只用 pnpm；锁文件是根目录 `pnpm-lock.yaml`。增删依赖用 `pnpm add` / `pnpm remove`，并随变更更新锁文件，不手工伪造。
- 密钥和环境差异通过安全配置管理；仓库只保留不含真实值的示例。
- 依赖用户输入构造命令、查询、路径或标记时，使用当前技术栈提供的安全参数化方式。
